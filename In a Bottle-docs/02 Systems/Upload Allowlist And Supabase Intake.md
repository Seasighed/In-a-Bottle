# Upload Allowlist And Supabase Intake

The public upload path is a narrow intake system for built-in release surveys. It does not turn imported surveys into remote collection forms.

## Client Eligibility

`SurveyUploadEligibility` owns the client-side upload gate. It loads `res://Resources/Survey/UploadAllowlist.json`, resolves each entry into an identity key, and compares that key against the active survey.

The identity key is:

```text
survey.id::v<survey.template_version>::<survey.schema_hash>
```

The bundled allowlist can leave `schema_hash` blank when it also provides a built-in `template_path`. In that case the client resolves the id, version, and hash through `SurveyTemplateLoader.describe_template_file`.

Eligibility rules:

- Built-in `res://` surveys can upload only when the resolved identity matches the allowlist.
- Imported `user://survey_templates` surveys are `Custom Survey` entries and cannot upload in v1.
- Missing survey id, template version, schema hash, template path, or allowlist file blocks upload with a visible reason.

Both the Journey shell and the classic shell use this helper before showing or enabling upload actions.

## Upload Payload

The client continues to send the existing `SurveySubmissionBundle` JSON. The bundle preserves:

- `survey.id`
- `survey.template_version`
- `survey.schema_hash`
- `client_payload_hash`
- quality metadata
- scrub-identifying-information state
- optional volunteered profile fields when the user opts into profile upload

Scrubbed identifying answers must stay scrubbed before the payload reaches the endpoint.

## Supabase Edge Function

The scaffolded endpoint is `POST /survey-upload` under `supabase/functions/survey-upload`.

The function:

- accepts JSON only
- rejects browser uploads from origins outside `SURVEY_UPLOAD_ALLOWED_ORIGINS`
- parses `SURVEY_UPLOAD_ALLOWLIST_JSON`
- validates survey id, template version, and schema hash before storage
- requires `client_payload_hash`
- rejects malformed payloads and unknown survey identities with stable reason categories
- checks duplicate payload hashes within the same survey identity before insert
- applies a conservative per-install daily upload limit when configured
- logs private rejection telemetry in `survey_upload_rejections`
- returns JSON with `accepted`, `response_id`, `survey_id`, `reason`, `endpoint_version`, and `message`

The server allowlist must contain the exact schema hash generated by the Godot loader for the deployed `MapleStory Pulse` template. The current release-candidate hash is `c69e1f63dd9480f644261067dbbf8d4e46d4d6f390702e58ccba8b2748a74c37`. Re-run `PrintSurveyIdentity.gd` after any template edit.

## Storage

`supabase/migrations/20260629170000_create_survey_responses.sql` creates `public.survey_responses` with private raw intake rows:

- response id
- survey id
- template version
- schema hash
- payload hash
- client install id
- submitted timestamp
- quality metadata
- scrub flag
- volunteered profile
- raw JSON payload

Row level security is enabled with no public policies. Public sharing should come from manually reviewed aggregates and wrapped exports, not direct table reads.

The same migration creates `public.survey_upload_rejections` for private rollout diagnostics. It stores rejection reason, message, endpoint version, origin, survey identity fields when available, payload hash when available, install id when available, and timestamp.

## Tests

`supabase/functions/survey-upload/validation.test.ts` covers accepted allowlisted payloads, unknown survey ids, wrong schema hashes, malformed payloads, duplicate-relevant payload-hash validation inputs, and scrub/profile preservation at the validation layer.

Godot CI covers the built-in upload eligibility path, the blocked Custom Survey path, and upload bundle identity preservation.

`supabase/functions/survey-upload/smoke.ts` is the live deployed-endpoint harness. It requires explicit `SURVEY_UPLOAD_SMOKE_WRITE_OK=true` because accepted and scrubbed smoke cases create private rows.

As of the release-candidate proof pass, local backend validation uses:

```powershell
deno test supabase/functions/survey-upload/validation.test.ts
deno check supabase/functions/survey-upload/index.ts supabase/functions/survey-upload/smoke.ts
```

Deployment uses `npx supabase` on this machine because `supabase` is not installed on PATH. A real deploy still requires a Supabase access token or login, project ref, local `supabase/survey-upload.env`, and the hosted origin.
